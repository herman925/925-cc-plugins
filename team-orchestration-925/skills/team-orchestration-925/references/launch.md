# Review and launch workers

Call `shared_team_status`. If `info.upgradeRequired`, offer the explicit native-reviewed `shared_team_upgrade` operation before a plan; normal status never upgrades the store. Keep its operation ID and reconcile an uncertain upgrade. If no store or team exists, use the normal reviewed creation flow. An approved controller can launch workers even when it is not itself a bound member; this grants no permission to perform member tasks.

Inspect the selected visible team with `shared_team` / `inspectConfiguration`. Ask which unconnected local **Codex workers** should start. The candidate supports native Windows Orca terminals and independent dispatcher-owned Codex app-server connections. It does not launch Claude or Hermes, remote members or the top member. Use connect for currently verified existing sessions; independent discovery does not adopt arbitrary external conversations. Capacity always queues; do not evict or auto-close sessions.

Build a command of type `approveLaunchPlan` with `teamId`, a new `planId`, `workerToolPolicy: "team-worker-v1"`, current `expectedConfigVersion`, current `expectedControllerGeneration`, and `selections`. Each selection carries `memberId`, a fresh `launchId`, and the actual `expectedMemberGeneration`, `expectedOfficialGeneration`, `expectedNotesGeneration` from the roster/role rows. Re-reviewing an already queued reservation must retain its existing launch ID. For a bound native-launched worker selected for tool setup, retain its launch ID and supply its exact `expectedBindingGeneration`; this records setup pending and never creates a duplicate. Claimed starts cannot be replaced. Do not guess generations or use prompt text as an approval flag.

Pass that command and a stable `operationId` to `shared_team_launch`. Its native form displays the exact selection, roles, standing switches, model/effort, current capacity and access to the four worker tools: status, member API, own inbox read and own inbox confirmation. Approval is for that specific plan, not future workers or other tools. Decline/cancel/timeout creates no plan. Edits to a queued worker or role invalidate its old approval; show a fresh review before it starts. Approval of a process-only legacy plan does not grant tool access retroactively.

After commit, the connected adapter processes new launches promptly and checks the queue every 30 seconds. It claims capacity, creates an empty terminal, commits that terminal's native home/incarnation, then sends the Codex bootstrap command. The child uses its real native conversation identity to bind through that target before its first permission-hook decision. It calls status, inspects its team and official role, reads its own bootstrap inbox receipt and confirms the exact `readReceiptId` with `shared_inbox_seen`. Only the native adapter records readiness after those successful calls. No task admission, delivery or pickup clock starts before Ready. A bootstrap receipt accepts no task or mail on somebody else's behalf.

For independent Codex the same API claim precedes native creation. The project dispatcher owns the provider pipe across head-MCP disconnects. It creates a thread without model input, verifies the actual native process/thread, commits the target, then starts one durable bootstrap turn. Native project execution/approval settings remain in force; this plan grants no filesystem/sandbox change. Idle owned recipients can receive exact inbox-check pointers; their own inbox tools still perform acknowledgement. An uncertain create/bootstrap/wake remains reserved and is never replaced or replayed. Inspect pending native forms/questions through `shared_team_worker_review`; only the approved top head may relay a real human answer. Unsupported permission requests remain pending. A provider turn finishing never reports a shared task outcome or head acceptance automatically.

Bound-worker setup blocks new assignments while existing work can finish under still-valid access. The selected product behavior is to resume the same conversation when idle, preserving history and work, and stop if safe resume cannot be verified. Automatic native idle/resume support is not yet implemented; do not send `/exit`, stop a process, launch a replacement or claim the approved setup has activated. Report the pending setup explicitly.

`inspectConfiguration` exposes durable launch states, native targets and `workerReadiness`. `queued` waits for capacity or a valid review; `claimed` means starting or uncertain and continues consuming a slot; `bound` means a verified member binding exists. Binding is separate from Ready. A disconnected or expired readiness check retains capacity and blocks new work. A terminal/input receipt does not prove the model started or completed work. After any unknown native effect, inspect and report it; do not submit a new start or retry raw terminal input. Cross-restart automatic recovery of claimed/uncertain native effects is not provided by this increment.
