## 3. 本轮已经完成的行为

### 模型目录

- New team 从 Orca 原生目录取得各 CLI 的真实选项，不再只有 Default，不使用硬编码型号表或让大模型凭记忆列型号。
- 当前项目／主机需要已有至少一个 Codex 或 Claude Code session；任意一种即可，不要求两个 CLI 都打开。普通终端检查真实实例和 `isRunningAgent`，不会因为旧 launch identity 留在 shell 中就算有效会话。忙碌会话也有效。
- 普通终端场景首次遇到 structured unsupported 拒绝时，使用只读 `agentSession.restartResumable({})` 初始化目录 host，再重读目录。该路径不消费／继续／丢弃恢复 offer，不创建临时 Chat，不改 Chat UI 设置。
- 给新团队读目录时使用当前启动账户的 session-less 路径，不借用某个旧 Chat 固定的账户。terminal handle、provider 对话 ID、structured sessionId 从未混用。
- 本机实际读到 Codex 7 项：GPT-6.1-Sol、GPT-6-Astra、GPT-6-Sol、GPT-6-Luna、GPT-5.6-Sol、GPT-5.6-Terra、GPT-5.6-Luna。
- Claude Code 实际返回 4 项：ID 为 opus、fable、sonnet、haiku。本机 opus 显示名称是 deepseek-v4-pro，sonnet／haiku 显示名称是 deepseek-flash；这是当前自定义映射，不能强改成另一份官方名称表。
- 下拉框只显示前面的模型名称，**去掉括号里的 model ID**。内部保存和启动仍用原始 ID；effort 取自该模型的原生返回值。
- CLI 列出一个选项不等于该账户已成功执行过生成，也不等于模型已在某个成员会话中生效。

### 模型闪烁已经修复

之前页面每 5 秒检查状态，模型目录超过 30 秒就清空列表并重绘表单，因此出现“模型名称 → Default → 模型名称”的闪烁。这是本轮前面实现引入、后来已按用户反馈修复的行为。

现行规则：目录取得后保留，配置期间不做周期刷新；同一项目的状态检查不重绘配置表单。切换 CLI 使用已取得的对应目录，仅对尚未取得的所选 CLI 做有限重试。切换项目或用户主动 Refresh models 才请求新目录。用户可以在 Launch 前主动修改选择。

启动所需的新鲜会话／能力证据在后台单独核对，不清空或替换已选模型显示。**显示稳定不等于取消原生启动验证。** 不要为了证据新鲜度重新加入 30 秒清空列表或整个表单反复重绘。

### Lead 与 Worker 名称

- Team name 下方有可选 **Lead name**，支持英文／中文逗号分隔。去除首尾空白，数量须匹配 Leads，名称输入不自动改写 Leads 数字。
- 数量不符、空项、重复或与其他成员重名时阻止创建。合法名字立即出现在 Organisation preview，并进入真实名册和启动信息。
- Leads = 3、Lead name = `UI, Dev, Review`：一个 Head 下有 UI、Dev、Review 三位 Lead。
- UI 下的三个 Worker 为 `UI-Worker-1`、`UI-Worker-2`、`UI-Worker-3`；其他 Lead 下分别从 1 编号。
- Leads = 1、Lead name = `UI`：唯一主管名称是 UI、角色仍是 Head，下面同样是 `UI-Worker-1…3`，没有额外中间 Lead。
- Lead name 留空时沿用原默认编号。已保存的旧团队不会因升级自动改名。
- 名称用于识别成员，不自动赋予 UI／开发／审查等专业职责；具体分工仍由主管根据任务决定。

Roster 仍是全员只读监控，只有 Add team／Open supervisor 等既定入口。新队固定 All at start。正常后续交办在有效主管会话中继续，不恢复面板总目标、Attention、个人管理、模板或每个目标新建对话。

## 5. 下一会话先用人话引导用户做什么

用户明确说不理解“四人混合”，已经解释为：**1 个主管用 Codex，3 个 Worker 用 Claude Code，四个 AI 一起完成任务。混合指团队里用了不同 CLI。** 后续说明继续用这种表达，不堆 Run／Dispatch 等术语让用户自己排查；原生证据由 agent 在后台核对。

下一会话先读代码和当前状态，再给用户少量可操作步骤。建议第一队这样配置：

| 表单字段 | 测试示例 |
| --- | --- |
| 当前项目 | 用户准备实际测试的 Mac 本机项目／隔离测试文件夹；读取并展示真实选择，不依据本会话 cwd 猜测 |
| Team name | 一个未使用的测试队名，例如 `QA125-Local` |
| Lead name | `UI`，或留空；只有一位主管时不能填三个名字 |
| Leads | **1** |
| Workers per lead | **3** |
| Head CLI | **Codex** |
| Workers CLI | **Claude Code** |
| Model／Effort | 用户账户实际可用的选项；没有把握时继承 Default，不替用户选定昂贵模型或改账户配置 |

用户在 New team 点击 Launch team 后，应有一个主管和三个 Worker。具名为 UI 时，显示名称应为 UI、UI-Worker-1、UI-Worker-2、UI-Worker-3。四人表单没有单独的 Leads 模型行，因为唯一主管就是 Head。

**不要直接采用 Leads = 3 来做“四人测试”**：它会额外生成 Head，Workers per lead = 3 时合计 13 人。

接着请用户在主管会话给一个实际任务。例如：

> 在当前测试目录做一个简单待办事项网页，支持新增、完成和删除。请安排三个 Worker 分工，检查结果后向我汇总，并说明如何打开和验证。遇到必须由我决定的问题，请在这个主管会话问我。

这个任务是开场示例，不是本交接已发送的指令。优先使用隔离测试目录，避免让示例覆盖用户现有项目。正常工作只和主管交流，不需要用户分别给三个 Worker 发任务。

观察与后台核对重点：

1. 四个实际成员都按保存的项目／主机和选择启动，名字正确；打开四个 tab 或收到输入不等于 provider 已就绪。
2. 主管确实分工，Worker 实际执行并回报；后台核实真实会话、协调 Run、Task／Dispatch、完成回报及主管审核，不把模型口头声称完成当作执行证据。
3. 有问题时在主管会话提问并等用户明确答复；空结果、取消、超时、沉默都不算批准。按绑定 CLI 使用实际可用提问工具，不能为了强开工具修改模式。
4. 主管汇总并检查结果后，用户在该会话继续交办一个小修改，确认沿用有效主管会话／协调 Run，不需要面板提交下一目标，也不自动另建主管。
5. 收集受影响的新版工作流程证据，再安排 #125 的 A／B 项目焦点切换小场景。不要把单纯切换 New team 的项目提示当作已保存团队的 scope 验证。

用户说的是“下一会话开始”，**本交接不授权本会话先把四人团队启动好**。下一会话可在已明确的测试范围内持续调查、修复和核对证据；需要用户实际点击、切换项目或安排中断时，给清晰步骤，不重复询问能否阅读或调查。

## 6. #125 真正缺的是哪两件事

以最新 issue 正文及 [2026-10-16 核对评论](https://github.com/herman925/925-cc-plugins/issues/125#issuecomment-6214959287)为准：

- **新版主管会话流程的最小回归**：当前版本四人 All at start，直接交办、提问／明确回复、逐级回报、结果确认和正常后续交办。可把本轮新命名与所选模型的真实启动一起核对。
- **焦点切换实证**：已保存并绑定项目 A 的团队，在桌面切到 B 后执行／观测一次合法受控操作，核对 TeamWork、Run、Task／Dispatch、实际会话和 execution host 仍属于 A，没有误投或重复启动。记录焦点与操作的先后顺序，不能凭最终回到 A 的画面认定通过。

历史 Git／普通文件夹四人闭环、整机重启、45 秒物理睡眠、执行中 Stop 等已有真实记录，**无需要求用户重跑整套**。也不恢复已经取消的管理表单来凑旧验收清单。

旧现场可能有 `QA125-Focus` 等历史团队或 stale handle。先核对现有持久化与原生身份；不要按相同名字重新认定、清数据库 reservation、再次 Launch 绕过 unknown，或关闭不属于本次测试的会话。
