# Team Orchestrator — Orca plugin

An Orca plugin panel inspired by [925-cc-plugins / team-orchestrator](https://github.com/herman925/925-cc-plugins/tree/main/team-orchestrator), with the organisation tree and Setup → Models → Preview → Launch selection flow.

It is separate from that Claude Code mod (0.5.37), which runs inside each Claude Code session. The current source keeps new teams in its own SQLite database under the verified Orca profile. It neither imports nor overwrites the mod's `.claude/team-orchestrator/` files or the prototype's `team-definitions-v1` KV data. The source includes native roster preparation, admitted task dispatch, declared scope coordination and evidence reconciliation; the Claude mod remains a separate product.

Release **0.1.14** (strict SemVer `0.1.14`). The plugin now includes its local Node worker and runtime adapter. You do not install a helper application, rebuild Orca or apply a source patch. Automatic injection is conditional on the installed Orca build passing the compatibility checks below.

Roster is read-only monitoring with one **Open supervisor** entry per team; initial staffing and model choices stay in New team. The original mod has optional member actions, but this port deliberately leaves daily coordination to the highest supervisor. Existing backend records and recovery safeguards remain intact; removing their panel controls does not grant the supervisor additional powers.

## How it works

```text
Plugin panel on your PC
  → scoped runtime IPC adapter (in memory)
  → this plugin's Node worker on your PC
  → durable worker preparation → genuine native runtime IPC → durable settlement
  → Orca chooses the supervisor's terminal or structured session
```

The worker detects the local OS, application packaging, parent process and Electron inspector fuse. It activates its own parent Orca's loopback inspector, verifies the PID, application identity and architecture, optional build metadata consistency, Node SQLite capability, advertised runtime interfaces and existing native evidence schemas, then installs an in-memory adapter. It closes the inspector it activated after injection; an existing developer inspector is left alone. Disabled fuses, another process on the inspector port, missing required handlers, runtime capabilities or incompatible evidence formats stop injection. The installed application files are never rewritten.

The adapter binds only `herman925.team-orchestrator`'s approved Team panel. It forwards an envelope through the existing `workspace.readContext` action to this plugin's declared commands. It calls Orca's original panel handler first, preserving current session ownership, consent, capability and admission checks, then uses the original command handler. An already open panel is bound on its next genuine main-frame IPC request, reusing Orca's owner/panel/revision token without refreshing discovery or manufacturing a sender event. Subframe requests and undeclared operations are rejected. It restores its wrappers on plugin disable/removal. Orca restart also removes the in-memory adapter.

The adapter captures the desktop's selected workspace identity. The worker resolves its actual `hostId`, presents a project/host selection for confirmation, and persists that binding with the team. Later launches check the saved identity and host, independently of desktop focus. Missing host evidence is reported instead of being assumed local. CLI `active` selectors are deliberately avoided because they resolve from cwd, not desktop selection. The worker passes `ORCA_USER_DATA_PATH` from the verified parent Electron application's `getPath('userData')`, and restores Windows `APPDATA` from `getPath('appData')` for its child CLI. It does not guess a profile directory, copy the desktop's full environment or change system environment settings. These internal paths are omitted from panel ping and Initialise results. This also pins macOS/Linux and custom/dev profiles to the same desktop instance.

Launch invokes native `agent.launchReplay` through the retained genuine main-frame event. The worker first commits a frozen role/configuration/scope, stable native operation ID and exclusive member reservation to SQLite. Fresh host capabilities and saved scope are checked before the effect. Orca applies custom command/argument/environment settings itself and chooses terminal or structured mode; the plugin does not construct provider shell commands. Omitted model/effort and `agentArgs` inherit native settings, while an explicit null argument override remains distinct.

The saved **Preparation mode** selects **On demand** (highest supervisor and every existing department manager) or **All at start** (exactly the saved roster). Leads and workers in on-demand mode start when their real supervisor receives a task permit. Preparation is paced to preserve the host's 30-panel-admission/10-second budget; there is no added concurrent-worker limit. Its brief describes the team's persistent function and role, explicitly waits for a separate TeamWork objective, and does not instruct other members to start. Native returned identity is committed before optional terminal naming. Structured naming has no verified method in the pinned build, so the plugin keeps its own label and reports that limitation. Prompt journal/terminal handoff, provider observation and permission waits are separate facts. Structured provider observation remains unknown without a supported live stream; **Open verified session** opens the exact corroborated native session.

Terminal members receive a `team/member` title, for example `proposal/Worker-1`, after their exact native identity is verified. This applies to prepared members, workers first started for a task, and approved replacement terminals. Naming receipts prevent reconciliation or restart from repeatedly overwriting a later custom title; an unknown naming result is not automatically replayed. Superseded or historical terminal bindings cannot authorize renaming. Naming changes the Orca display title only: it does not discover a provider conversation ID or resume an old provider conversation. Structured conversations retain the naming limitation described above.

## Install or update

1. Use this folder on the **PC running Orca**, as your existing development plugin path. A checkout on the server alone is not automatically a local PC path.
2. Refresh **Settings → Plugins** and review/enable Team Orchestrator. Adding `main.mjs` changes Orca's consent to include **trusted Node worker code**. This worker has native process access, beyond the panel's declared host API capabilities.
3. Open the Team Orchestrator panel and check **v0.1.14**.
4. Orca starts workers lazily. An agent-status change or workspace-created event starts this worker and automatically injects the adapter. If the panel is opened on an idle desktop before either event, run the contributed Orca command **Team Orchestrator: Initialise local adapter** once. No external installer is involved. Bootstrap logs appear in this plugin's Orca logs.
5. The panel opens the roster only after the worker connection and saved team data are verified. If either fails, it shows one **Plugin unavailable** warning with **Retry** and optional **Details**, hiding navigation, cached teams and the empty-team screen. Normal connection diagnostics and **Test connection** live under **Settings → Connection**; OS, Orca version and worker PID are collapsed under **Technical details**.
6. In **New team**, choose the structure and preferences, confirm the project and host, then click **Launch team**. The roster appears after startup. Open the highest supervisor's session to give it work. Use **Open supervisor** on the team card to return to that conversation. Member names and the organisation chart are read-only; there is no member detail form.

The `main.mjs`, `runtime-adapter.cjs` and self-contained `panel.html` artifacts ship in this folder. Installation needs no npm packages or web server. The former manual patches and alternate manifest have been removed from this release; they remain in Git history.

If you see “plugin is not enabled with current consent”, first let any refresh finish and retry **Initialise local adapter**. If Settings → Plugins shows **Review required**, review/enable the plugin there. Version 0.1.05 removed the adapter's self-triggered refresh, added a live worker authority check before injection, and removed the unnecessary startup-status storage write that could poison bootstrap during a refresh. It does not alter or automatically approve consent.

## Features and recovery

- Roster, New team and Settings views; read-only organisation tree and highest-supervisor session navigation.
- Squad (4), All-Purpose Team (11), Tech Team (21), and custom team hierarchies.
- Head only; Head → Workers; Head → Leads → Workers; CEO → named Heads → Workers.
- One to five reports per manager, Codex or Claude Code, model and effort by level.
- Persistent UUID team/member identities, confirmed project/host bindings, and immutable configuration/role versions in `<verified profile>/plugins-data/herman925.team-orchestrator/team-orchestrator.sqlite`. The native worker is the single writer; `node:sqlite` is required.
- Version-checked semantic saves reject stale panels instead of overwriting another window. Same-name teams have independent identities.
- Read/schema/corruption errors block writes and preserve data. Legacy KV and mod data stay isolated; no automatic import occurs.
- Durable launch Operations and member reservations: intent before native effect, actual identity before naming, completed receipts reread without another launch.
- Unknown transport delivery retains the member reservation and is never automatically retried. Reload reads worker-saved handles from SQLite. Legacy coordinator requests are not imported or relaunched.

The internal `recoverLaunch` operation (formerly **Check saved launch** in the panel) is an observation, not a second native launch. It reads only the pinned original `agent-session-journal.db` schema-4 operation row from the verified profile, under the desktop caller namespace, and validates operation ID, native fingerprint and expiry. A genuine succeeded launch receipt can repair missing plugin settlement. Missing, pending, unknown, expired, mismatched or unavailable rows remain unknown/reserved; no call to effectful `agent.launchReplay` is used as a query. Existing success is returned independently of current preferences. A native failure remains reserved for explicit later recovery; this ticket does not create a new session automatically.

## Roster and supervisor conversation

Like the original Claude Code mod, Roster shows every registered member of launched teams in the selected project, including not-started, idle and unavailable members. It is not restricted to currently executing agents. Creation is in New team. Saved but unlaunched definitions are available there for recovery after an interrupted start.

The panel refreshes native observations about every five seconds while visible. It checks exact terminal handle/pane/PTY identity or structured session location/owner/fence before presenting activity. Permission/question waits display **Needs input**. Unknown or stale identity never inherits an old `working` launch observation. Polling cannot launch a member or resend a prompt. Opening the supervisor focuses its exact saved native session; it cannot recreate a closed or unverified session.

Structured sessions report context through native context facts: measured input/window usage, or an explicitly labeled estimate based on input plus cache tokens (never output tokens). Native `agentSession.options` provider-confirmed model/effort appear as reported values. Unconfirmed session options and launch configuration have a **set** label. The current terminal API reports activity but does not expose context or effective model/effort; those cells show **—** or labeled configuration instead of invented live values. Missing/unknown context is never rendered as 0%.

The three previous **Start team work**, **Submit total objective**, and **Next total objectives** flows were additions in this port, not original roster features. They are removed. New teams automatically initialize a durable supervisor coordination Run once their real saved session is ready. This setup contains no business assignment: the user gives tasks directly in that conversation, and the supervisor continues in the same Run between assignments. Questions, staffing and failures use the previously implemented supervisor-session decision path. It does not require a panel objective, delivery acceptance, or goal queue. Unknown setup delivery is never automatically resent; closed conversations are not reopened by setup. Internal native Task/Dispatch admission and parent review remain in force.

Legacy objective/queue/acceptance receipts remain readable and their domain recovery code is retained for existing history. They are not offered as new roster workflows. New coordination records use `mode: supervisor-session`; the legacy `sessionMode: false` setup is retained for old internal callers and regression fixtures.

## Compatibility limits

- Live acceptance is limited to the recorded macOS cases; Windows, SSH and 11/21-member scale tests remain separate. The runtime adapter uses private Electron IPC handlers and Orca's experimental plugin interface; an Orca update can break it.
- Injection currently targets the main-process inspector's default loopback port 9229. A disabled inspector fuse or an incompatible debugger setup cannot be repaired by this plugin.
- Role persistence is confirmed by the plugin's SQLite transaction. A model's claim to have written a role file is not used as persistence evidence.
- Nested manager Runs and stopped-instance replacement are separate lifecycle work. Managers calling the remote orchestration CLI need the corresponding SSH-host CLI permission. Session preparation alone does not confer native parent/Dispatch authority.
- Model/effort validity comes from the actual target catalog and native launch validation; no shared static provider effort list is assumed.

### Host-based agent preferences (#109)

Models now come from the saved project's native Orca capability reads. Level defaults and individual member overrides are saved as versioned requested preferences; changing a level leaves individual overrides intact. The panel offers preferences only in New team; backend override/inheritance operations remain for existing records and internal callers. Model IDs and effort choices follow each model's host catalog. Effective model, effort and context usage remain unknown until native session evidence is available; a saved selection is not an observation of a running provider.

The adapter retains the genuine main-frame event for a fixed set of native reads, rechecks the original panel gate, and authenticates internal observation phases with a worker-instance secret. Panel input cannot provide capability proof or choose arbitrary runtime methods. Refresh failures invalidate older evidence, and rate-limit refusals retain the original host code. Normal plugin consent and frame/owner checks still apply.

Default model/effort inherit Orca settings without clearing launch arguments. SSH executable detection uses the saved target, with a separate connectivity check. The pinned host does not expose a trustworthy remote model catalog through the desktop model-catalog method: SSH catalog availability stays unknown, inherited defaults remain usable, and explicit model/effort overrides stay gated until verified. TUI picker visibility is displayed as configuration, not treated as a blanket structured-provider prohibition. Configuration and role collaboration rules do not intercept provider tools.

Evidence: source/service tests, opaque-frame browser tests, pinned source-schema checks, and a separate Electron fixture exercise these paths. They do not establish actual provider, SSH, or Windows acceptance. Native launch effect admission and later effective-value observation continue in the following implementation tickets.

### Native task admission (#112)

After the actual supervisor Run is verified, the worker sends a separate generation-bound dispatch protocol. The supervisor creates a native Task intent for a registered direct report and waits. The plugin checks the native Task creation receipt/hash, actual supervisor identity and Run generation, then commits the member reservation and exact role/configuration/task attempt before sending a user-input permit. The supervisor alone runs native worker-start. Plugin code never creates a Run, dispatches as the supervisor or emits worker_done.

Native Task/Dispatch/worker identity and accepted worker-report evidence populate internal task records and roster observations. Execution success or failure stays pending supervisor acceptance; that later decision is separate. Duplicate observations do not resend permits. Ambiguous input and missing/changed native evidence remain reserved; work already started before admission is shown as unadmitted uncertainty. One native session cannot become two registered members' bindings.

Terminal members receive the Orca sidebar title `Team/Member` (for example, `proposal/Worker-1`). Prepared terminals are named after their launch identity is saved; on-demand workers are named after their admitted native Dispatch and current exact terminal instance are verified. Approved replacement terminals use the same naming format. A durable display-only naming attempt prevents polling or restarting the plugin from repeating a rename, including when its receipt is lost; existing prepared/reused titles and later manual renames are preserved. Naming failure does not change task execution or acceptance. Closed Work and superseded instances are not renamed. Native `terminal.show`/`list` titles may be generated OSC titles rather than the sidebar's custom title. Structured chat naming remains unavailable; these titles do not discover provider conversation IDs or enable provider resume.

The protocol is cooperative orchestration, not a provider-tool sandbox: native work outside the app admission flow is not retroactively adopted. Native evidence is read from the verified profile with a fixed read-only schema43 reader. Structured actor hashes and terminal creator tuples follow the pinned host's identity rules; ordinary model JSON and tab names are not authority. Background checks use the existing private user-control transport and normal current plugin consent. Real provider, SSH and Windows acceptance remain separate human validation; fixtures prove only the stated transport/state/contract seams.

### Direct supervisor acceptance and rework (#113)

Native execution results remain immutable attempt records. The direct supervisor reviews the result and validation references, then uses its own native `task-update` with the unchanged terminal status and the issued review protocol. The plugin verifies the actual native mutation hash, current Run generation, supervisor identity, Task/Dispatch, attempt token and evidence references before saving an independent acceptance event. Task and member views show the reviewer, decision, time and evidence. A panel click or model JSON without that native proof cannot accept a task.

Task intents can declare `dependencies` as stable application `taskKey` values. Native `completed` does not release these dependencies; only the latest attempt's verified `accepted` decision does. Rework uses a new native Task under the same `taskKey` and a `previousAttemptId` naming the current rejected attempt. The original result and decision remain readable after refresh or restart, and late reviews cannot finish the new attempt.

Sequential work retains the member reservation and verifies the existing session before issuing an exact `--terminal` reuse permit. Structured sessions use their native canonical address and session fence; PTYs require the saved process incarnation, pane, provider and scope. Reuse omits agent/model/effort overrides. An unavailable or changed session blocks the new attempt instead of authorizing another launch. Prepared all-at-start sessions use that same native target path: canonical `orca_session_id:` for structured sessions or the verified PTY process. Their native resource ownership is external; worker-release must not be assumed to close them. Stopped-instance recovery is a separate lifecycle feature.

Validation uses real plugin SQLite with native-shaped fixture ledgers, browser interactions, the pinned native TaskUpdate parser/hash and target normalization, and isolated Electron user-control transport. The fixtures never authorize a claim of real Orca/provider, Windows or SSH execution acceptance.

### Interruption reconciliation

Opening the panel or restarting the plugin worker rereads saved member operations and exact native Run/Task/Dispatch evidence. A launch intent that has not passed the durable submission boundary is shown separately from an uncertain submitted operation. Native creation receipts establish an effect, while current liveness remains a separate observation. Recovery never calls a launch, resume, replacement or inbox-consumption method. `workerShow` and `workerRead` may reconcile native old-epoch states into unknown; their observations do not authorize replacement.

Member and task cards retain the evidence source, last observation, exact task/attempt references and incomplete-output warnings. Archived output is labeled and never used as current liveness evidence. Missing rows, timeouts, disconnected SSH hosts, released leases without exact owner-fence death evidence and changed identities keep the member and its scope reserved. Check the saved launch/work or inspect its verified native session; recovery does not offer a supposedly safe duplicate launch.

Native socket observations pin one runtime ID across metadata reads, request writes and response settlement, including same-process runtime rotations. SSH observations also check connection generation before and after the read and immediately before input. SQLite compare-and-set versions reject late panel observations. Member binding generations increase monotonically; retiring an application recipient pointer preserves history and does not claim that its native session stopped. Old receipts can add historical evidence but cannot republish a retired member binding or replace a newer execution instance. Execution results and supervisor reviews remain immutable when recovery evidence changes.

## Parallel task scheduling

Every new Task intent declares `writeScope: [{path: "src", kind: "directory"}]` or file entries; `[]` explicitly declares no writes. Paths are relative to the shared selected Git workspace or ordinary folder. No member worktree is created. Overlapping declarations wait until the latest attempt is accepted. Pending acceptance, rework and unknown results retain their scopes. Dependencies wait for application acceptance, not native completion. These declarations coordinate cooperating agents; they do not enforce filesystem isolation or block undeclared writes.

When the host advertises native queued-message support, permits for a busy structured supervisor use `queue-if-active` with a fingerprinted delivery policy. Queued input is displayed separately from actual member execution. Queued task cards show scope, dependency, capability and member-reservation reasons beside active tasks. A failed or unavailable member does not stop independent nonconflicting work. Preparation and task permits preserve stable request identities; reopening the panel never repeats unknown effects. **Continue roster preparation** resumes members with no saved operation, while existing operations stay reserved. Prepared sessions retain their requested provider/model/effort, and reuse permits omit launch overrides.
### Decisions in the highest supervisor conversation

The user discusses questions, staffing and failure escalation in the highest Head/CEO session. There is no Attention page or panel answer/approval form. The roster provides **Open supervisor session**, escaped read-only conversation history and member recovery controls. Lower managers relay questions and proposals through their actual hierarchy.

The plugin sends `TEAM_SESSION_DECISIONS` instructions to an already-running highest supervisor once per current epoch/generation, including the current native Run and protocol. Pending legacy questions, their previous answers, and staffing proposals are delivered to that same session. The actual bound supervisor CLI determines the question tool: **Codex → `request_user_input`**, **Claude Code → `AskUserQuestion`**. Editable preferences for a future launch do not change this choice. The supervisor checks whether its tool is exposed and permitted in the current mode; if unavailable, it asks in the same conversation and waits for an explicit reply. It never changes modes or feature flags to force availability. Empty answers, cancellation, timeout, preselected options and silence cannot authorize staffing or another execution. It then uses the existing `orca orchestration task-create --spec JSON --run RUN --json` interface with `team-questions/v1` and one of these kinds:

- `session-answer`: exact question ID/revision, answer body, explicit supplement flag and optional specific next native Task after two failures.
- `staffing-decision`: exact proposal ID/native Task ID, configuration version and approve/reject choice.
- `session-resolution`: exact obsolete question and verified recovery ID, with the user's resolution note.

All three include a stable decision ID, current protocol token/generation, `userConfirmed: true` and `userStatement`. The trust boundary is explicit: native receipts authenticate the actual highest supervisor recording the user's answer, **not an independently authenticated user-message or provider question-tool receipt**. The supervisor must obtain the real user's answer in its own session, never infer consent from silence or another agent. Child managers, forged receipts, stale authority, missing confirmation and mismatched proposal/question versions cannot authorize changes. The plugin returns `TEAM_SESSION_DECISION_RESULT` in the same conversation, with no second panel confirmation. Rejected decisions remain rejected; correction uses a new decision ID. Lost notice delivery is preserved without automatic resend.

Worker questions retain their exact native Task, Dispatch, attempt and owning Run. Recording a session answer does not impersonate a manager or resume a worker: its real owning manager still replies, nested relays must be verified, and the answer remains pending until those replies are observed. A highest-supervisor decision grounded in a verified worker completion report has no native requester to resume. An explicit processed session supplement can supersede only earlier report answers that were blocked before any send; unknown or attempted delivery is never silently discarded. Legacy panel answers already queued before this migration retain their original delivery and acknowledgement semantics.

Two consecutive proven execution failures still block only the affected task. The supervisor explains the failure and options in its session; a recorded explicit user decision naming the exact next native Task authorizes that step. Independent tasks continue. Read-only conversation history preserves decisions and older blocked answers; supervisor recovery keeps the original evidence and requires an explicit session resolution for obsolete questions.

Automated validation covers authenticated native SQLite receipts, terminal and structured session paths, restart/replay, the local socket, host contracts, browser UI and a separate Electron fixture. It does not establish live provider, Windows or SSH acceptance.

## Pause and exact native stop

Team and member **Pause new assignments** controls persist scheduling admission independently from native execution. Resume permits queued independent work again. Pausing never closes a conversation or cancels a running task. A permit already received by a real supervisor remains a previously admitted operation.

**Stop current execution** records an immutable member/instance and, where applicable, TeamWork/Run/Task/Dispatch selection before effect. The main adapter rechecks actual panel ownership and native consent, uses the authenticated native socket, and preserves the stop UUID as top-level `orchestrationRequestId` for `orchestration.workerStop`. It never supplies a fabricated supervisor caller. Standalone local terminals use `terminal.stopExact` for one verified PTY with `targetOnly` and `keepHistory`; only a positive post-stop census confirms exit. Structured close requires an already established owner fence and exact native death evidence. Remote standalone stops and bindings without sufficient native identity are unsupported.

A submitted request, native assignment stopped, a closed view, and proven execution exit remain separate.
