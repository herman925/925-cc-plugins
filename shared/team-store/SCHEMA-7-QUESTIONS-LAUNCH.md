# Schema 7: bounded questions, deadline notices and fresh member launch

Schema 7 extends the released schema-6 preview through an explicit, backed-up update from schema 5 or 6. The frozen schema-6 definition is kept solely for inspection and backup recovery; ordinary open still refuses older stores.

Questions use `threads.thread_kind=question` and a snapshotted `answer_window_minutes`. A task may have one open work thread and one open question thread per endpoint pair. Team coordination questions have a team owner and their own Run. No owner transfer or peer bypass is added. Task questions require an active current attempt and its current head/worker endpoints.

`askQuestion` supplies teamId, threadId, runId, assignmentId (null for team coordination), recipientMemberId, question and the normal config/member/binding generations. For task questions the existing task Run is authoritative. `inspectQuestion` is restricted to the endpoints. `answerQuestion` supplies threadId, answer, expectedThreadGeneration and the normal authority fields. Recipient read starts the database-clock deadline once. A conditional open-to-answered transition admits one winner; an expired question cannot be answered. Reply content is immutable and its delivery owns read/replay state. Terminal question threads may deliver their newly created status reply, but their original question is fenced and cannot replay.

`observeDeadlines` catches up expired questions and unfinished assignments. `deadline_notices` records observer events separately from worker-authored messages. Only the addressed recipient can `acknowledgeNotice`; inspecting another member never clears it. Notices remain recoverable after missed wake-ups, and the client applies the team's replay rate to native wake reservations. Client timers run every 30 seconds and resume after restart; this is not a database daemon or a background scheduler when all clients are closed.

`member_launches` is a per-member durable queue: queued → claimed → bound, with immutable identity and monotonic generations. Only a privately verified approved controller reserves/claims a launch. The model-facing command catalogue rejects these private operations. A fresh claim receipt may initiate one external native create after commit. It is never replayed as another external effect. Existing bindings and uncertain starts count against the team's machine-local cap. The native effect uses the exact verified project home and a reserved Claude conversation ID. The child uses its own native caller/OS-parent proof to bind that reservation; a display name is never binding evidence. A verified resume of that same reserved conversation can refresh its transport incarnation without another launch.

Windows uses an encoded PowerShell command and a private settings file, avoiding legacy native-argument corruption of inline JSON. POSIX uses quoted individual arguments. The settings file enables shared mode only for this project and preserves the chosen executable paths. No permission bypass flags are added. A failed or unknown native effect stays claimed for operator inspection; it is not automatically retried, evicted or reclaimed from contact loss. Automatic liveness-based capacity reclamation and existing-member replacement are outside this increment.

Database guards prevent launch identity changes, backward state transitions, deletion and alternate-key replacement. Deadline-notice identity/content is immutable, acknowledgement cannot be rewritten, and replay time cannot go backward. These guards and explicit upgrades are exercised on SQLite and PostgreSQL. Orca-plugin integration, hosted Mod configuration, legacy-file migration and the deferred full automatic model lifecycle remain separate.
